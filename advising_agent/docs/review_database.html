Registrar database review

Review of the data layer in 1emb/AgenticAI_project2 at commit 5ab1cda: the 12-table schema, its documentation (the schema page and README), and the seed dataset in data/seed/. Written from the Advising agent side, 2026-10-29.

Verdict

The schema is clean and well documented, and the seed data passed every integrity check I ran. The main problem is scope, not quality. Without an enrollment (grades) table, most of what the project slides ask for cannot be answered, and the README now declares the schema frozen for the agents. I recommend adding enrollment before agent work goes further. The README already proposes its shape, and the generator is deterministic, so the test sets can be rebuilt.

What I checked

  • Models, the initial migration, README, docs/domain.md and the schema page.
  • About 30 automated checks over all 11 seed CSVs (1,660 rows).
  • An end-to-end run: the Advising agent planned one active student in each of the 4 programs, straight from the seed data, and an independent validator re-checked every plan.

Findings, most severe first

Critical

No enrollment or grade table, and the schema is frozen

Without it there is no transcript, GPA, standing, "can I add", roster, grade statistics, graduation check or dismissal check, and the advisor cannot see what a student has taken. The README lists these as pending. About two thirds of the slide needs depend on this one table.

Fix: add enrollment(term_code, crn, student_university_id, status, grade FK grade_scale) as proposed in the README, seed it from the generator, and regenerate data/testset. Freezing the schema before this table exists locks in a system that cannot meet the assignment.

High

No advisor-to-student assignment

Advisors are a user type in the slides, and the professor question catalog mentions advisees. Nothing in the schema says who advises whom, so "show my advisees" or an advisor viewing a student's plan cannot be permitted or refused correctly.

Fix: a column student.advisor_university_id (FK instructor), or a table advisor_assignment(student_university_id, advisor_university_id, start_term_code) if history matters.

High

MS prerequisites point outside the MS degree plans

MSCS has a required course whose prerequisite is CS 3310, and MSENG one whose prerequisite is ENG 3110. Neither course is in the MS plan, and there is no record of a student's prior degree or transfer credit. Any prerequisite check for an MS student will be wrong: either "prerequisite not met" for every MS student, or the check silently skipped. The Advising agent found this on the real data: both MS programs came out infeasible until I added a policy switch.

Fix: decide and document one rule, either "admission to an MS program satisfies undergraduate prerequisites" or a prior_credit table. The Advising agent currently uses the first, as an explicit policy parameter.

Medium

Category-minimum semantics are not written down

BSCS needs 25 general-education credits, and 7 of its required courses (ENGL 1110, ENGL 1120) are general education. Does the 25 include those 7, or come on top of them? The difference is 7 credits in every graduation check. The README defines core but not this case.

Fix: one sentence in the README, plus an example. The Advising agent counts all rows of the category, required ones included.

Medium

Agents can read SSNs

person.ssn is stored raw, which is fine as a synthetic leak marker for the test sets. But nothing at the database level stops an agent's SQL from selecting it, so protection rests entirely on prompts and code. The same applies to date of birth and sex, which no agent use case needs.

Fix: a database role for the agents with REVOKE SELECT (ssn, date_of_birth, sex) ON person, or a view person_public without those columns that the agents use. This is cheap, and it makes the access-control test cases hold even when a prompt fails.

Medium

No catalog year on degree plans

docs/domain.md says degree audits run "by catalog year", but degree_requirement has one plan per program. A student admitted in Fall 2021 is audited against today's plan. That's acceptable for frozen synthetic data, but it should be stated as an assumption so the agents don't claim catalog-year behavior.

Low

Constraints the data obeys but the schema does not enforce

  • Policy dates in order (registration opens < start < add < drop < withdraw < end < grades due).
  • lecture.start_time < end_time, capacity > 0, credit_hours > 0.
  • suggested_term_number BETWEEN 1 AND 8 (documented, not checked).
  • course_prerequisite.min_grade is a foreign key to grade_scale, so W or I would be accepted as a minimum grade.

Fix: CHECK constraints in a new Alembic revision. They protect the next regeneration, not today's data.

Low

Summer is in the enum but not in the data

All 20 terms are fall or spring, and the summer term code is still undefined. Either define the code (for example a 60 suffix) or remove summer from the enum, so that agents do not offer summer plans the data cannot support.

Low

Lectures stop at Spring 2027, terms run to Spring 2031

This is reasonable, since future schedules are not published. Agents must then treat later terms as projected from the offering history and must not cite CRNs for them. Worth one line in the README.

Checks that passed

  • No prerequisite cycles; every prerequisite references an existing course.
  • No lower-division course requires a higher-level one.
  • Course level matches course number in every row.
  • Term sequence contiguous; dates ordered; no overlapping terms.
  • No instructor and no room double-booked in any term.
  • No duplicate (term, course, section); every days value valid.
  • Inactive courses (2) and inactive instructors only in past terms.
  • Every active course has lectures; every BS required course runs in fall and spring.
  • No inactive or graduate-level course in a BS plan.
  • Suggested terms always come after their prerequisites.
  • Every category minimum can be met from the listed courses (MSENG exactly: 21 of 21, no slack).
  • IDs, SSN format, unique emails; every person has a role.
