Advising Agent: interface and design

What the Advising agent needs from the Router, the Data agent and the Policy agent, what it returns, and how its ASP planner works. The code in advising_agent/contracts.py is the typed version of this page; keep the two in sync. Last updated 2026-10-29 against the 12-table schema and seed data (commit 5ab1cda).

1. Role in the system

The Advising agent answers "what should this student take, and when can they graduate?". It turns the student's record, the degree plan and the course offerings into a multi-term plan. An ASP solver (clingo) builds the plan, and plain Python checks it again independently. The LLM only writes the explanation from the finished result. The agent never writes to the database.

Data and Policy agentsread-only rows; typed policy parameters with citations
Router, then userAdvisingResponse; CRNs go to Registration only if the user asks

The Policy agent's RAG supplies the citations. The NMSU-based handbook should change some values from the real NMSU ones, so the prior-knowledge test in the evaluation can detect answers that ignore retrieval.

7. ASP planner (asp/advising.lp)

Facts, generated from the input by facts.py

Credits and grade points are integers in tenths (3.0 credits is 30, C- 1.7 is 17), because ASP has no decimals.

Hard constraints

  • Each open course at most once, only in a term where it is offered (a non-full, non-cancelled lecture in published terms; the offering history in projected terms), and only at an allowed level.
  • Every prerequisite group is met before the term (by a completed grade at or above the minimum, a course in progress, or an earlier planned course).
  • In published terms: exactly one open section per course, no two sections overlapping.
  • Credits per term at most max_load; at least min_load except in the last term; nothing after the hard target.
  • By the end of the plan: all required courses, every category minimum, and the program's total credits.

Objectives, lexicographic (higher first)

  1. Fewest terms (earliest graduation).
  2. Fewest avoided courses and sections on avoided days or times.
  3. Most preferred courses.
  4. Fewest planned credits (no padding).
  5. Tie-break: take courses earlier.

Beyond one plan

  • Relaxation ladder: if there is no plan, the agent drops the hard target, then plans more terms (keeping the student's credit cap), then drops the credit-cap preference, and stops at the first that works. relaxed[] lists exactly what changed.
  • Cautious consequences: a second run with only objective 1 computes must_take_next_term, the courses that appear next term in every earliest-graduation plan.
  • Alternatives: clingo enumerates optimal models (--opt-mode=optN, projected on the shown atoms). With all five objectives the optimum is often unique, so plans_found is often 1; dropping objective 5 gives more alternatives.
  • Independent check: validate.py re-checks every plan in plain Python without using the encoding. The Registration agent can reuse it for a single term.

Performance and what makes it fast

  • Candidate courses: only degree-plan courses, their prerequisites (transitively) and preferred courses are choices. If they cannot reach the program's total credits, generic "FREE ELECTIVE n" slots of 3 credits fill the gap, used in order to avoid symmetric plans.
  • Counting check before solving: if the credits still needed exceed the per-term cap times the usable terms, the horizon is infeasible without a solver call. The same count gives grad_lb, so the graduation term is proven as soon as a plan reaches it. Proving such bounds inside the solver is a pigeonhole argument, which CDCL solvers handle badly.
  • Time limit: 10 s for the main solve and 10 s for the cautious run. On timeout the best plan found so far is returned, validated and flagged.
  • A stored term without lecture rows is planned as projected (its schedule is not published yet).

Known limits

  • Projected terms assume the past offering pattern holds; sections and seats are only checked in published terms.
  • Every planned course is assumed passed with the prerequisite minimum, so the plan is a best case.
  • The program's minimum GPA is reported, not planned, since future grades are unknown.
  • No corequisites, transfer credit or holds yet (not in the schema).

8. Test cases

fixtures/example_requests.json holds 10 requests with expected results. They cover a hard target that cannot be met, a plan with no target, an advisor allowed, an instructor denied, a student asking about another student, a suspended student, a horizon that is too short, a credit cap that is too low, a request with no preferences, and a missing field. Run pytest advising_agent/tests -q. tests/test_scale.py is an opt-in stress test on a generated 200-course, 120-credit program (RUN_SLOW=1 pytest advising_agent/tests -q, 10 to 20 s); it checks that the plan is valid and the graduation term is proven.

Proposed shape for data/testset (persona student, intent plan_graduation), following its verification contract:

"answer": {"allowed": true, "status": "ok",
           "earliest_graduation_term": "Fall 2028",
           "must_take_next_term": ["CS 2730"],
           "remaining_required": ["CS 2730", "CS 3720", "CS 4710", "CS 4740"]}

Several plans can be optimal, so the grader should check these invariants and run validate.check_plan on the agent's plan, not compare one plan exactly. If the ground truth also comes from this solver, the check is partly circular; a few hand-checked cases and the independent validator reduce that risk.
