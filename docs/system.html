Agentic AI Registrar Office: full system

How the parts fit, how to run them, and what was tested, on branch advising-agent of 1emb/AgenticAI_project2 (on top of the team's commit b473fc9, "Student Agent"). 2026-11-03.

1. Architecture

Login (role from the session)scripts/registrar_chat.py --user ID [--role]. The role is checked against the database; a TA with two roles picks one.
Router registrar/agents/router.py: builds the persona agent for the role and adds the shared tools.
Student agentteam (F. Ahmad): catalog, sections, degree plan, calendar, refusals. Added: transcript, GPA, plan_my_degree, search_policy.
Professor agentnew: teaching schedule, load, capacity, catalog, colleagues, refusals; advisees only via plan_for_advisee.
Administrator agentnew: grade distributions, DFW, extremes, withdrawals, fill, probation and at-risk lists, graduation candidates, headcount, cohorts.
SharedAdvising agent (ASP planner + validator, advising_agent/); Policy agent (handbook retrieval + parameters).
PostgreSQLteam's 12 tables and seed data, plus enrollment and advisor_assignment (new Alembic revision, synthetic data). The handbook and its parameters live in data/policy/.

Design rules, kept from the team's Student agent

  • The model never types the graded answer. Tools return the answer shape; the agent assembles it from tool results.
  • Permissions are enforced in the tools, not in the prompt. No tool returns another student's record, a student list (except to the administrator), or private instructor fields. A refusal's target is recorded for grading and never shown to the model.
  • Numbers come from code: GPA, statistics, standing and plans are computed in Python, SQL or ASP. Rule values come from data/policy/params.json; the handbook text supplies the citations, and a test checks that the two agree.

4. Synthetic enrollment data

  • Each student is simulated term by term from the admit term. Courses follow the degree plan's suggested order, then category courses, then free electives. A course is taken only when every prerequisite group is met at its minimum grade, and, from Fall 2024 on, only in a non-cancelled section with a free seat.
  • Grades come from a per-student ability, the student's status, the course level and occasional bad outcomes. Low grades and Fs are repeated, and about 3% of enrollments end in a W.
  • Graded through Spring 2026. Fall 2026 is in progress with no grades, and Spring 2027 has no rows, matching the test sets' default clock.
  • Terms before Fall 2024 have no lecture rows, so their enrollments have crn null. Adding older lectures would have changed the professor test set's teaching history.

Fixes the live runs led to:

  1. The loop drops tool arguments the tool does not declare. The small model added e.g. course to no-argument tools, and the calls failed.
  2. The Ollama client retries when the model runner is killed (out of memory on this 7 GB machine); the server cache uses q8_0.
  3. Admin tools validate and normalize program and entry_type; "all" was being treated as a program code.
  4. Prompts and parameter descriptions say to add a filter only when the user names it.
  5. The router's grounding check: a turn with no successful tool call gets one corrective message. A refusal's target is resolved from the question when the model leaves it out.
  6. Admin tools normalize confused scope kinds, e.g. course with value MATH becomes subject MATH. Not yet measured live.

The remaining held-out failures are the model's choices: a wrong tool (a calendar date for "is X offered"), a guessed course for a CRN question, or a wrong refusal reason. None is a crash, a leak or an invented number. Every graded value came from a tool. Expect higher scores with the team's 30B model.

6. Known issues and limits

  • Test-set conflict (professor): course_catalog and the access_allowed/prerequisites scenario use the same question, "What are the prerequisites for X?", but expect different shapes under the same key: records with min_grade vs plain codes. A live agent can pass only one of the two. Fix in the generator: rename one key.
  • Test-set issue (student, found by the team): CRN questions without a term that expect Spring 2027 at a Fall 2026 clock.
  • Administrator catalog: written for an older 53-table schema. Colleges, gen-ed areas, waitlists, overrides, holds, incompletes and graduation applications don't exist here, so those intents are dropped. "Graduating" means "meets every requirement once this term's courses are passed".
  • Same author on both sides: I wrote both the admin tools and the SQL ground truth. Agreement proves consistency, not that the rules are the ones the team wants. The rules are written in registrar/agents/admin/tools.py for review.
  • Synthetic handbook: its numbers were chosen for this project and are not NMSU's. The prior-knowledge check from the design (rules that differ from what a model may know) still needs values that deliberately differ from NMSU's.
  • Advisors: the professor test set treats "I'm their advisor" as a claim to refuse. With advisor_assignment, a real advisor may plan for their own advisees. No existing case targets a real advisee (checked), so no case changes.
  • The live model here is qwen3 1.7B on 2 CPU cores, chosen because it fits. It is not the team's qwen3-coder:30b, so the live numbers are a floor for the system, not its expected accuracy.
